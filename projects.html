[RKE2 k8s 클러스터 Grafana 모니터링 스택 구축] — Prometheus 메트릭 + Loki + Alloy syslog 파이프라인과 DGX Spark(GB10) 서버 연동

2026.07

Prometheus Grafana Loki DGX Spark(GB10) vLLM Alloy RKE2
개요
  • RKE2 v1.35.6+rke2r1 클러스터에 monitoring 네임스페이스를 신규 생성하고 Prometheus(메트릭) + Loki(로그) + Alloy(syslog 수집) + Grafana(시각화) 통합 모니터링 스택을 구축.
  • 사내 Local LLM이 설치된 NVIDIA DGX Spark(GB10) 추론 서버 3대(대전 1대 / 서울 2대)를 하나의 대시보드에서 관측하도록 프로메테우스 메트릭·로그 파이프라인을 연동.
역할
  • 인프라 엔지니어(모니터링 스택 아키텍처 설계 및 K8s 매니페스트 작성·배포 전담)
  • DGX 서버 사전 구성: 포트 충돌(9100 vLLM 점유)로 node_exporter를 :9101로 분리, GB10 hwmon 콜렉터 비활성화 후 nvidia-smi 기반 GPU textfile collector 스크립트·systemd 서비스 작성(수집 시간 0.07초로 단축)
  • 로그 파이프라인 구성: DGX rsyslog omfwd(RFC5424 + octet-counted) → Alloy NodePort 30514 → relabel(host/app/level/facility) → Loki push
  • Grafana 데이터소스·대시보드 자동 프로비저닝 및 HAProxy Ingress(TLS) 연동
성과
  • AS-IS: GPU 추론 서버의 자원 사용률·온도·스로틀 상태와 시스템 로그를 서버에 직접 접속해 확인해야 했고, 3개의 DGX 서버의 모니터링이 필요로 함.
  • TO-BE: Prometheus 메트릭 + Loki 로그를 Grafana 단일 화면에서 상관 분석 가능한 환경을 구축하여 DGX Spark(GB10) GPU 온도·전력·클럭·냉각 스로틀과 vLLM 추론 지표를 실시간 관측.
  • Prometheus 30일 / Loki 720h 보관 정책과 총 170Gi PVC 설계로 안정적인 장기 관측 기반 마련.
개선점
  • 저는 처음에 node_exporter의 기본 콜렉터를 그대로 사용했으나, DGX Spark GB10에서 hwmon 콜렉터가 전체 수집 시간의 57%(142.8ms)를 소모한다는 것을 스크레이핑 지연을 추적하며 발견했습니다. 이 경험을 통해 모니터링 에이전트도 대상 하드웨어 특성에 맞게 콜렉터를 취사선택하고 필요한 /sys 경로만 직접 읽도록 튜닝해야 한다는 것을 체득했습니다.
  • DGX 로그가 Loki에 수신되지 않아, Alloy의 syslog 파서가 RFC5424 + octet-counted 조합을 요구하는데 rsyslog 기본값(RFC3164)으로 전송되고 있었음을 확인했습니다. 앞으로는 로그 파이프라인 구축 시 송신·수신 양단의 포맷 규격을 먼저 합의하고 검증해야겠다고 느꼈습니다.

역할

  • 운영 내부망 CLUSTER에 Jenkins CI 도구 설치
  • 이슈 대응 및 트러블슈팅 지원(부사수역할): 특정 파드 "v2-6-istio-cni": Unauthorized 에러 로그 발생 및 ContainerCreating 상태 유지 문제 트러블슈팅
    • 해결 : 공식적으로는 OSSM 2.4 이상에서 해결된 사안이나 kubeconfig 파일의 인증 정보 갱신 실패 등 불안정 요소로 인해 OpenShift 4.16 클러스터 버전에서 발생할 수 있는 요소로 확인됨 istio-cni-node 파드 재기동으로 해결

    • 해결 : 실제 해당 지역 교육청에서 Pod가 사용하는 CIDR IP 대역과 겹쳐서 통신이 되지 않는 상황이었으며 Infra Node에서 Layer4 Packet의 SRC에 Client IP가 직접적으로 노출됨을 확인. 정상적으로는 VIP가 노출되어야 하는 상황으로 해당 지역 교육청에서 트래픽이 유입되는 L4 장비에 SNAT(Source NAT, 출발지 네트워크 주소 변환) 설정을 적용하여 Pod IP 대역과 겹치지 않도록 조치.
성과
  • Private OpenShift Cluster의 실무 안정적인 운영 경험을 축적했습니다.
  • 실제 운영상에 발생하는 Pod 기동 시 에러 로그 및 OpenShift 플랫폼 네트워크 이슈 등을 트러블슈팅하며 안정적인 OpenShift 운영에 기여했습니다.
